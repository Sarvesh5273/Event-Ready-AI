# EventReady AI - Final Frozen Build Spec

Last updated: August 10, 2026

Status: **Final direction. No more ideation loops. Build this.**

Project: **EventReady AI**

Hackathon: **YouCam API Skin AI & Apparel VTO Hackathon**

Primary demo scenario: **Wedding Guest**

Core product:

> EventReady AI is an occasion-first wedding guest shopping assistant that uses YouCam Skin Analysis and YouCam Apparel Virtual Try-On to select, simulate, and rank 3 VTO-compatible outfits from a curated catalog.

One-line winning pitch:

> EventReady AI turns virtual try-on from "how does this look?" into "which look should I confidently choose for this event?"

Core thesis:

> People do not shop for skincare or outfits in isolation. They shop for confidence before a moment that matters.

---

## 1. Final Verdict

The idea is good enough to win.

Stop debating the concept. The remaining risk is execution.

The winning version is not:

> A generic virtual try-on app.

The winning version is:

> A wedding guest decision assistant that combines Skin AI, Apparel VTO, and explainable selection logic to help a shopper choose the best outfit for a high-stakes social event.

The primary demo must show:

- A visually compelling occasion.
- Three visibly different outfit try-ons.
- A real or replayed YouCam Skin AI result.
- Real or replayed YouCam Apparel VTO results.
- A simple but honest rule-based recommendation.
- No fake claims of trained ML or predictive return modeling.

## 2. Frozen Scope

Build only these features:

1. Wedding Guest occasion flow
2. Two preference inputs:
   - Style vibe: `Classic` or `Bold`
   - Budget tier: `Low`, `Mid`, or `High`
3. Demo persona and demo images
4. Curated catalog of 9-12 VTO-compatible wedding guest outfits

6. YouCam Apparel VTO integration
7. Selection of 3 outfits from the catalog
8. 3 Apparel VTO outputs
9. Explainable confidence heuristic
10. Positive, non-medical appearance guidance
11. Devpost-ready README, screenshots, and demo video

Do not build:

- Retailer dashboard
- Product scraping
- Auth/login
- Checkout
- Marketplace
- User closet
- Social sharing
- Friend voting
- Calendar integration
- Weather integration
- Native mobile app
- ML training
- Complex analytics
- More than one primary occasion in the demo

Secondary occasions may appear visually in the UI as disabled or "coming next" options, but they should not consume engineering time.

## 3. Why Wedding Guest Is Final

Use **Wedding Guest** as the primary scenario.

Reasons:

- It has strong visual variety.
- It supports different silhouettes:
  - Floral midi dress
  - Satin slip dress
  - Tailored jumpsuit
  - Structured blazer set
  - Soft pastel dress
  - Bold statement dress
- It lets the demo show obvious differences between VTO outputs.
- It is familiar enough for judges to understand instantly.
- It connects naturally to skin, outfit, camera readiness, and confidence.

Do not use Job Interview as the main demo.

Reason:

- Interview outfits are visually conservative.
- Three dark blazers will look too similar in a 1-3 minute video.
- The VTO "wow" moment becomes weak.

Do not use Gala as the main demo.

Reason:

- It is visually strong but narrower and less relatable than Wedding Guest.

Do not use First Date as the main demo.

Reason:

- It may be too casual and less clearly tied to apparel retail value.

## 4. Hackathon Judging Alignment

### Technological Implementation

Use both required strengths:

- YouCam Skin Analysis
- YouCam Apparel Virtual Try-On

Make the integration non-trivial:

- Skin analysis affects outfit candidate selection and ranking.
- VTO creates the visual comparison.
- A rule engine combines:
  - occasion rules
  - skin signals
  - garment metadata
  - user preference inputs

Avoid fake sophistication.

Say clearly:

> The prototype uses an explainable v0 confidence heuristic, not a trained prediction model.

### Design

The app must feel like a complete consumer flow:

1. Pick event
2. Pick vibe and budget
3. Upload photos or use demo persona
4. See AI processing
5. Compare 3 try-ons
6. Get one recommendation with reasons

No retailer panel in the product UI.

Retail value belongs in:

- Demo video narration
- Devpost writeup
- README

### Potential Impact

Real problem:

- Online fashion shoppers are uncertain before buying.
- Event-based purchases create urgency.
- Many virtual try-on products show an image but do not help decide.

Impact claim:

> EventReady AI reduces purchase uncertainty before high-stakes social events by helping shoppers choose the best outfit with visual try-on and explainable personalization.

Secondary retail impact:

> The same decision data could help retailers understand hesitation, rejected products, and conversion risk.

Do not claim:

- It predicts actual returns.
- It clinically evaluates skin.
- It guarantees fit.
- It guarantees better purchases.

### Quality of Idea

Non-obvious angle:

- Occasion-first, not garment-first.
- Skin + outfit integrated in one decision.
- Explainable recommendation, not just image generation.

Judges should remember:

> This team used YouCam APIs as decision infrastructure, not as a visual gimmick.

Do immediately:

2. Sign up for YouCam API.
3. Verify email.
4. Redeem the hackathon code.

Blocker:

Fallback:

- Build explicit Demo Mode using fixed demo persona and replay data.
- But the final repository must still contain real API integration code.

### Task 2: Make One Real Skin AI Call

Before writing skin rules:

1. Use one test selfie.
2. Call YouCam Skin Analysis.
3. Save the raw response.
4. Inspect the actual `score_info.json` or equivalent output.
5. Confirm score names, score ranges, and missing-field behavior.

Do not guess thresholds before this.

The current rule table is provisional until calibrated from real API output.

### Task 3: Make One Real Apparel VTO Call

Before building all 3 outfit flows:

1. Use one full-body demo image.
2. Use one clean garment image.
3. Call YouCam Apparel VTO.
4. Poll until success.
5. Save the generated result image.
6. Confirm latency and result format.

### Task 4: Source VTO-Compatible Garment Images

Find or create 9-12 garment images.

Requirements:

- Clean white or neutral background.
- Single garment or outfit visible.
- Front-facing.
- Clear edges.
- No busy lifestyle photo.
- No model in complex pose if avoidable.
- No logos or trademarks.
- No copyrighted brand imagery unless licensed.
- Correct garment type for VTO.

Bad garment image examples:

- Influencer photo wearing dress outdoors.
- Catalog photo with complex background.
- Cropped garment.
- Side-angle pose.
- Multiple items overlapping.
- Watermarks.
- Brand logos.

Good garment image examples:

- Dress on white background.
- Jumpsuit front view on neutral background.
- Mannequin or flat-lay with clean edges.
- Full outfit product image with no distractions.

This is a critical curation task.

### Final Asset Sourcing Decision

Use a rights-safe generated asset pipeline unless a fully licensed source is already available.

Required assets:

1. 9-12 garment images
2. 1 demo persona selfie
3. 1 demo persona full-body image
4. 3 replayed VTO output images after live testing

Recommended garment source:

- Generate clean product-style garment images with AI image generation.
- Prompt for front-facing, full outfit, white/neutral background, no model, no logos, no text, no watermark.
- Manually reject anything with distorted garment structure, cropped edges, logos, text, or messy backgrounds.

Backup garment source:

- Use only stock/product images with clear commercial rights and no visible trademarks.
- Prefer flat-lay, mannequin, or product-only shots.
- Do not use lifestyle photos from real retailers unless the license explicitly allows this use.

Recommended demo persona source:

- First try a generated demo persona because it avoids consent and rights issues.
- Test the generated selfie with YouCam Skin Analysis on Day 1.
- Test the generated full-body image with YouCam Apparel VTO on Day 1.
- If YouCam rejects synthetic-looking images or produces poor results, use a real consenting team member's photos.

Consent rule for real photos:

- If a real person's selfie/full-body image appears in the public demo video, screenshots, repository, or submission, get explicit permission from that person.
- Do not use a friend's or stranger's photo informally.

Asset naming:

## 7. Demo Mode Policy

Demo Mode must be explicit.

Never show cached results from another person's uploaded photo.

### Live Mode

Live Mode behavior:

- User uploads their own selfie and full-body photo.
- App calls YouCam APIs.
- Cache results only for the same uploaded image hash and selected garment IDs.
- If user uploads a different image, do not reuse old VTO images.

### Demo Mode

Demo Mode behavior:

- Fixed demo persona.
- Fixed demo selfie and full-body image.
- Fixed catalog.
- Fixed replayed YouCam outputs.
- Clear banner:

```txt
Demo Mode: using saved YouCam API results from a test session.
```

This is acceptable if transparent.

### Replay Cache

Use replay cache to save API units.

Cache key examples:

```txt
skin:{hash(selfieImageBytes + requestedActions)}
vto:{hash(fullBodyImageBytes + garmentImageBytes + garmentCategory)}
```

Rules:

- Cache successful results.
- Cache failed results only for a short time.
- Never use one user's generated body image for another user's upload.
- Demo persona replay is allowed only in explicit Demo Mode.

## 8. Technical Architecture

Recommended stack:

- Next.js
- TypeScript
- Tailwind CSS
- Server-side API routes
- No database for the hackathon MVP
- Local or simple object storage for demo assets
- Vercel or Render for deployment

Simplest build:

```txt
Next.js app
  Frontend pages/components
  Backend API routes
  lib/youcam service layer
  lib/scoring rule engine
  lib/catalog curated products
  demo replay JSON and image assets
```

### Final Persistence Decision

Do **not** use SQLite for the deployed hackathon MVP.

Reason:

- A serverless deployment should not depend on persistent local filesystem writes.
- The session lifetime is only one demo run.
- Avoid database setup, migrations, and deployment persistence bugs.

Use stateless session state instead:

- Browser stores the current session state in memory/localStorage.
- Backend returns a signed session token containing:
  - session ID
  - preferences
  - selected outfit IDs
  - YouCam task IDs
  - status summary
- Each status request sends the signed token back to the server.
- Server verifies the signature, checks YouCam task status once, returns updated status and a new signed token.

Signing:

- Use `SESSION_SECRET` in environment variables.
- Sign with HMAC.
- Do not put the YouCam API key in the token.
- Do not put private user images directly in the token.

Demo Mode persistence:

- Demo Mode uses static replay files from `public/demo/replay`.
- No database needed.

Local development:

- If a local replay cache is useful, store it under `.cache/` and keep it out of the deployed architecture.
- Do not make local cache required for production.

### Final Polling Decision

Do **not** use a blocking polling loop inside `analyze/route.ts`.

Correct route behavior:

```txt
POST /api/sessions/:sessionId/analyze
  - Starts Skin Analysis task if not started
  - Starts VTO tasks when prerequisites are ready
  - Returns immediately with task IDs/status token

GET /api/sessions/:sessionId/status
  - Verifies signed session token
  - Performs one status check per outstanding YouCam task
  - Updates status
  - Returns immediately
```

The browser polls `/status` every few seconds.

Why:

- Avoid serverless function timeout risk.
- Avoid making users wait on a single long request.
- Make partial progress visible.
- Make failed individual VTO tasks recoverable.

Allowed use of a polling helper:

- A blocking `pollUntilComplete` helper is allowed only in local scripts used for Day 1 API experiments.
- It must not be used in deployed request handlers.

## 12. Skin Signal Calibration

This section is intentionally provisional.

Do not finalize thresholds until a real Skin AI response is inspected.

### Expected Process

1. Make a real Skin Analysis API call.
2. Save the raw result as:

```txt
public/demo/replay/skin-result-raw.json
```

3. Inspect:

- field names
- score ranges
- whether higher score means more concern or better condition
- missing fields
- whether output is JSON directly or ZIP containing JSON

4. Update `normalizeSkinSignals()`.

### Placeholder Threshold Pattern

Only use this after confirming score direction.

```ts
function toLevel(score: number | undefined): SkinSignalLevel {
  if (score === undefined) return "unknown";
  if (score >= 67) return "high";
  if (score >= 34) return "medium";
  return "low";
}
```

Warning:

- This threshold is arbitrary until calibrated.
- In code comments and README, call it a v0 heuristic.
- Do not claim scientific accuracy.

### Required Code Honesty

Add README language:

```txt
The prototype normalizes Skin Analysis outputs into low/medium/high signals using transparent thresholds. These thresholds are used only for styling and appearance-readiness guidance, not medical diagnosis.
```

## 13. Skin-To-Outfit Rule Logic

This is the heart of the technical differentiation.

### Rule Table

| Skin Signal | Outfit Rule | User-Facing Language |
|---|---|---|
| High redness | Prefer cool or neutral tones: navy, sage, teal, emerald. Penalize warm red/orange near face. | "Cooler tones create a calmer face-framing effect for this look." |
| High oiliness | Prefer matte or soft-sheen fabric. Penalize high-shine satin/sequin looks. | "A lower-shine fabric is more camera-stable for long event lighting." |
| High dark circles/eye bags | Prefer stronger contrast near face. | "The neckline and color contrast help keep attention on the full look." |
| Low radiance/moisture | Prefer softer tones and avoid harsh visible cautions. | "A softer palette keeps the look polished without feeling severe." |
| High texture/acne | Do not show direct acne warnings. Use confidence-positive language only. | "This look keeps the focus on silhouette and overall polish." |

### Important Language Rules

Never say:

- "Your acne is high."
- "Your skin is bad."
- "You need treatment."
- "Use salicylic acid."
- "Use retinol."
- "You look tired."
- "Your skin score is poor."

Allowed:

- "For event lighting, a matte finish may photograph more consistently."
- "Cooler tones create a calmer face-framing effect."
- "A gentle hydration-focused prep can help makeup sit more evenly."
- "This recommendation is cosmetic, not medical."

### Generic Prep Tips

Keep these short and safe:

```txt
Use a gentle, familiar routine before the event.
Choose a matte or balanced finish if the venue has bright lighting.
Do a quick photo check in similar lighting before leaving.
Avoid trying harsh new products immediately before the event.
```

No ingredients.

No diagnosis.

No medical claims.

## 14. Outfit Selection Algorithm

Goal:

- Select exactly 3 outfits from the catalog.

Inputs:

- User style vibe
- User budget tier
- Normalized skin signals
- Catalog metadata

Selection should be partly personalized before VTO.

### Selection Rules

Start with all catalog items tagged `wedding_guest`.

Add points:

- +3 if `styleVibe` matches user preference or is `either`
- +2 if `priceTier` matches budget
- +2 if color/fabric matches skin signal rule
- +1 if silhouette gives visual diversity

Subtract points:

- -2 for budget mismatch
- -2 for warm tone when redness is high
- -2 for high-shine fabric when oiliness is high
- -1 if too similar to already selected outfit

Final selection:

- Pick top candidate.
- Pick second candidate with different silhouette.
- Pick third candidate with different color family and style energy.

Important:

- The 3 outputs must look visually different.
- Do not pick three similar dresses.

Pseudo-code:

```ts
export function selectOutfits({
  catalog,
  preferences,
  skinSignals,
}: {
  catalog: CatalogItem[];
  preferences: UserPreferences;
  skinSignals: NormalizedSkinSignals;
}): OutfitCandidate[] {
  const scored = catalog
    .filter((item) => item.occasionTags.includes("wedding_guest"))
    .map((item) => scoreCatalogItemForSelection(item, preferences, skinSignals))
    .sort((a, b) => b.score - a.score);

  return pickDiverseTopThree(scored);
}
```

## 15. Confidence Heuristic

Do not call this an AI model.

Name:

```txt
Explainable Confidence Heuristic v0
```

Purpose:

- Summarize why one look is recommended.
- Make the recommendation transparent.
- Give judges code they can inspect.

### Formula

Use only variables the app actually collects or computes:

```ts
confidenceScore =
  occasionFitPoints +
  styleVibePoints +
  budgetPoints +
  skinOutfitFitPoints +
  vtoSuccessPoints -
  cautionPenalty;
```

Then clamp to 0-100.

Suggested point ranges:

```txt
occasionFitPoints: 0-25
styleVibePoints: 0-20
budgetPoints: 0-15
skinOutfitFitPoints: 0-25
vtoSuccessPoints: 0-10
cautionPenalty: 0-20
```

### Why This Is Better Than Weighted Formula

Avoid:

```ts
0.4 * eventFit + 0.25 * skinOutfitFit
```

Reason:

- Arbitrary weights look fake if presented as scientific.

Prefer:

```txt
This prototype assigns transparent points for each visible decision factor.
```

That is honest and easy for judges to inspect.

### Example Score Output

```json
{
  "catalogItemId": "emerald_jumpsuit_mid",
  "confidenceScore": 87,
  "reasonCodes": [
```

## 17. YouCam API Integration Plan

### Official Docs

Use the current YouCam docs while implementing:

- YouCam API documentation: https://docs.perfectcorp.com/develop/introduction
- Skin Analysis: https://docs.perfectcorp.com/reference/ai_skin_analysis/v2.1
- AI Clothes Virtual Try-On: https://docs.perfectcorp.com/reference/ai_clothes/section/overview

### Skin Analysis

Expected service file:

```txt
src/lib/youcam/skinAnalysis.ts
```

Responsibilities:

- Accept selfie image URL or uploaded file reference.
- Start Skin Analysis task.
- Poll task status.
- Download/parse result if needed.
- Return normalized raw response to app.

Important:

- The exact response must be inspected from a real API call.
- Do not finalize thresholds from documentation guesses.

### Apparel VTO

Expected service file:

```txt
src/lib/youcam/clothesVto.ts
```

Responsibilities:

- Accept full-body user image.
- Accept selected garment image.
- Start Apparel VTO task.
- Poll task status.
- Return result image URL.

Known docs mention endpoints in the `cloth-v3` family, including:

```txt
POST /s2s/v2.0/file/cloth-v3
POST /s2s/v2.0/task/cloth-v3
GET /s2s/v2.0/task/cloth-v3/{task_id}
```

Verify exact base URL, auth, request body, and parameters from the current console/docs before coding final calls.

### Polling

Use browser-driven polling against server routes.

Never poll YouCam directly from the browser.

Do not use this blocking helper inside deployed routes:

```ts
export async function pollUntilComplete<T>({
  poll,
  timeoutMs = 120000,
  intervalMs = 3000,
}: {
  poll: () => Promise<T & { task_status?: string }>;
  timeoutMs?: number;
  intervalMs?: number;
}) {
  const startedAt = Date.now();

  while (Date.now() - startedAt < timeoutMs) {
    const result = await poll();

    if (result.task_status === "success") return result;
    if (result.task_status === "error") {
      throw new Error("YouCam task failed");
    }

    await new Promise((resolve) => setTimeout(resolve, intervalMs));
  }

  throw new Error("YouCam task timed out");
}
```

That helper is only acceptable in local test scripts.

Deployed route pattern:

```ts
export async function GET(request: Request) {
  const session = verifySignedSession(request);
  const updatedSession = await checkEachOutstandingYouCamTaskOnce(session);

  return Response.json({
    sessionToken: signSession(updatedSession),
    status: buildPublicStatus(updatedSession),
  });
}
```

The frontend handles repeated polling:

```ts
setInterval(() => {
  fetch(`/api/sessions/${sessionId}/status`, {
    headers: { Authorization: `Bearer ${sessionToken}` },
  });
}, 3000);
```

## 23. Devpost Submission Draft

### Inspiration

People rarely shop for outfits in isolation. They shop because a moment is coming: a wedding, gala, interview, date, or celebration. Existing virtual try-on tools show how a garment looks, but they often stop before helping the shopper decide which look is actually right for the occasion.

### What It Does

EventReady AI is an occasion-first wedding guest shopping assistant. A user chooses a simple style vibe and budget, uploads a selfie and full-body photo, and receives three AI-generated outfit try-ons from a curated wedding guest catalog.

The app uses YouCam Skin Analysis to extract appearance-readiness signals and YouCam Apparel Virtual Try-On to generate realistic outfit previews. An explainable confidence heuristic ranks the looks using occasion fit, style preference, budget tier, skin-to-outfit rules, and VTO success.

### How We Built It

We built EventReady AI as a full-stack web application with server-side YouCam API integration. The backend handles API authentication, task creation, polling, replay caching, and response normalization. The frontend provides a focused consumer flow from occasion setup to final recommendation.

The recommendation engine is intentionally transparent. It uses human-readable reason codes rather than pretending to be a trained model.

### YouCam APIs Used

- YouCam AI Skin Analysis
- YouCam AI Clothes Virtual Try-On

### What Makes It Different

Most virtual try-on projects start with a garment. EventReady AI starts with the occasion. It combines skin signals, event context, and outfit simulation to help users make a confident decision.

### Challenges

The hardest parts were selecting VTO-compatible garment assets, handling asynchronous API polling, and designing skin-informed styling logic without making medical or attractiveness claims.

### Impact

Event-based apparel purchases are high uncertainty. EventReady AI reduces that uncertainty by moving from visual novelty to explainable decision support. The same reason-code data could eventually help retailers understand hesitation, rejected products, and conversion risk before checkout.

### What's Next

Future versions could support more occasions, retailer catalog integrations, trained decision-risk models, AI Look Virtual Try-On, and post-purchase feedback loops.
